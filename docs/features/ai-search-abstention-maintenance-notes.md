# 动态语料中的拒答与 Bench 维护：讨论稿

核对日期：2026-11-06。本稿区分已核实文献与项目建议；未实施新的线上维护策略，未修改冻结用例或历史记录。

拒答首先是相对于问题、可用证据、时间及来源要求的决策。“本站当前资料不足”不能推出“现实中没有答案”；现实正确也不自动等于满足本站的引用约束。

## 已核实的一手做法

**学术界先界定可回答性的参照物。** SQuAD 2.0 的不可回答指给定段落不支持答案。ICLR 2025 的 Sufficient Context 进一步把“上下文是否充分”与“模型回答是否正确”分开：模型可能凭参数知识在证据不足时答对，也可能在证据充分时答错。因此，“没有依据但碰巧正确”与“编造了错误事实”应分开统计；本产品仍可依据证据约束拒绝前一种输出。[SQuAD 2.0](https://aclanthology.org/P18-2124/)、[Sufficient Context](https://arxiv.org/html/2411.06037v2)

**拒答率不能单独说明系统好坏。** Selective QA under Domain Shift 用 risk–coverage 衡量“回答了多少”与“已回答部分错多少”的权衡，并说明分布变化下模型置信度可能失准。它区分给定证据不可回答与模型容易答错；两者不能共用一个含糊的“模型不知道”。[ACL 2020 论文](https://aclanthology.org/2020.acl-main.503/)

**可控负例比未经验证的“应该没有”更可靠。** GovTech 的 KnowOrNot 从已知事实构造问答，再移除对应事实，测试证据缺失时的拒答；同时分别评估是否拒答与未拒答时的事实正确性，并用人工抽样验证自动评估。它依赖事实间足够独立的设计；移除一条评论后，重复帖、父评论或其他段落仍可能泄露答案，必须检查。作者也指出，无参考答案的随机合成问题不适合直接评估事实正确率。[论文 §2.2、§3.4](https://arxiv.org/html/2505.13545v1)、[作者代码](https://github.com/govtech-responsibleai/KnowOrNot)

**动态世界需要带日期的答案版本。** FreshQA 面向易变化事实与错误前提问题，作者仓库保留不同日期的旧版本。可借鉴的是题目、答案和评测时间一起版本化；不能据其更新计划断言任何时候都严格按周更新。[FreshLLMs 论文](https://arxiv.org/abs/2310.03214)、[FreshQA 历史版本](https://github.com/freshllms/freshqa/blob/main/README.md)

**工业工具把离线比较、线上监测及故障位置分开。** LangSmith 使用整理过的数据集做离线版本比较，线上真实交互做监测，并将失败 trace 回流离线集。Microsoft Foundry 分开评价文档检索、回答与证据的一致性、相关性和完整性；这些维度不能由一个总通过率代替，也不能把模型评分当成人工 gold。[LangSmith 官方评测流程](https://docs.langchain.com/langsmith/evaluation)、[Microsoft RAG evaluators](https://learn.microsoft.com/en-us/azure/foundry/concepts/evaluation-evaluators/rag-evaluators?view=foundry)

## 对本项目的建议（尚未实施）

把问题的预期绑定到 `case_version + corpus_revision + question_time + evidence_policy`。另记本轮检索是否获得充分证据，不让 top-k 结果决定全库标签：

| 实际状态 | 应如何评价 |
|---|---|
| 库内已核对有答案，但本轮漏召回 | 用户侧可以暂不作答；评测记检索失败，不算成功拒答 |
| 相关证据已送达，模型仍拒答 | 记不必要拒答，检查筛选、作答或核验阶段 |
| 指定版本、范围内确无充分证据 | 正确拒答；只陈述已核查的资料范围 |
| 接口失败或超时，未完成取证/核验 | 记运行错误，不能算正确拒答 |
| 新数据可能改变原标签，尚未核对 | 记待复核，单列数量与原因；不自动改答案，也不掩盖模型/API 失败 |

维护两套用途：本地固定库与原始 18 条预期保留，比较算法回归；线上动态集独立发版，回答“当前服务表现如何”。006 新增回复、007/016 补到适用时段的官方材料、008 日期窗口进入数据范围，都应触发对应预期的复核，不能直接沿用旧库的负例结论。

时间还需区分发布日期、适用日期和抓取日期。当前代码以“所问月份晚于最新帖子时间”硬拒绝部分官方问题，属于待讨论改进：旧公告可能提前覆盖未来月份，最新论坛评论也未必具备官方依据。应检查明确适用时段与来源资格，本轮不直接改变规则。

每轮保留题目/参考答案版本、原文与摘录、代码/索引/模型及参数版本、帖子和评论的范围与数量、数据变更标识。记录运行前后版本；若运行中变更，标明不是严格同一快照。需要严格复现时另用一致的只读快照；仅有最新帖子日期或文件修改时间不能完整代表数据库状态。只保存少量参考证据可复现作答检查，不能复现全库召回竞争。

指标至少分别报告：无依据作答、不必要拒答、已回答部分的事实/引用正确性、召回缺失、待复核及 API 错误；逐项保留分母。18 条开发集不足以证明总体风险或校准稳定阈值。新标签先依据源记录复核，再发新版；旧成绩与失败不覆盖。线上先手动触发，自动付费重测与保留周期另议。
