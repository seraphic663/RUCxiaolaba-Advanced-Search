# ID 台账与列表刷新方案

状态：已接入现有 crawler/scheduler；`crawler/ledger_monitor.py` 仍是本地一次性建表工具，Railway 使用现有 quota-friendly scheduler，不启动第二个独立爬虫。

本地 2026-08-12 的初始 list1 建表记录了 397 个唯一 ID，源端 `create_time` 覆盖 `2026-08-10 19:14:57` 到 `2026-08-12 07:02:25`（北京时间，约 35 小时 47 分钟）。这说明初始 20 页是一个按帖子创建时间排序的约 36 小时内容窗口；线上重新建表时应以 `post_id_ledger` / `crawler_run_history` 实际记录的边界为准，不能把这个时间段硬编码成永久结论。

## 1. 一句话方案

初始阶段先固定扫描 `lists` 20 页，只把 ID、首次来源、首次发现时间和列表元数据写入台账，并把唯一 ID 按发现顺序放入详情队列；详情再由单 lane 低速补全。20 页扫描使用持久化的 `lists_bootstrap_next_page` 游标，每成功提交一页就前移，遇到额度停止或进程重启时从下一页续扫，不重复消耗已经完成的页。基线完成后，先在队列中记录一次 monitor cutover：切换时刻以前的普通 coverage 详情任务暂停，priority 0 的新回刷新和切换后新增 ID 仍可领取；随后先补一次 `lists`，再启动 `lists`/`lists2` 低强度监视。详情接口一次返回正文、评论和回复结构，队列按 `post_id` 去重，避免两个 cookie 对同一帖子重复抓取。

这里的“旧 cookie”和“新 cookie”是两个已获授权会话的调度 lane，而不是伪造身份或绕过上游限制的机制。每个 lane 都必须独立记录请求量、错误和限流状态；某个 lane 被限流时应暂停该 lane，不能自动把它伪装成另一个身份继续冲额度。

## 2. 已确认的 API 事实

| API | 作用 | 已观察到的返回 | 计划中的职责 |
|---|---|---|---|
| `/article/article/lists?page=N` | 新发列表 | 顶层包含 `list`、`page`、`pageSize`、`total`；单页通常 20 条 | 发现新 ID、维护创建时间和列表快照 |
| `/article/article/lists2?page=N` | 新回/活跃列表 | 返回结构与 `lists` 类似；包含 `id`、`update_time`、`count_comment` 等 | 观察已有 ID 的变化并触发必要的详情刷新 |
| `/article/article/info?id=帖子ID` | 帖子详情 | 返回正文以及评论/回复结构 | 获取正文、评论和回复的完整快照 |

当前实测中两个列表接口的有效深度约为 100 页，`pageSize` 为 20，`total` 会在 1999/2000 左右波动；请求第 101 页时曾被上游压回有效的第 100 页。因此“100 页”应被视为本轮扫描上限，不应被理解为永远存在的固定数据总量。

列表项已经包含 `id`、`create_time`、`update_time`、`count_comment`、`count_star`、`count_trace`、标题、用户展示字段等元数据，但列表项不是详情快照，不能据此认为已经获得了全部评论或回复；要获取评论结构仍需调用一次详情接口。

## 3. 请求量和覆盖量的正确换算

列表“观察记录”与详情“实际抓取”必须分开计算。一次列表请求最多观察 20 条记录，但这些记录可能重复；一次详情请求通常对应一个去重后的帖子 ID，并由一次响应带回正文、评论和回复。

| 扫描安排 | 列表请求数/日 | 理论列表观察数/日 | 详情请求上限的计算方式 |
|---|---:|---:|---|
| `lists` 100 页一次，`lists2` 100 页一次 | 200 | 约 4000 | 只对新 ID 或符合刷新条件的已有 ID调用详情 |
| `lists` 100 页一次，`lists2` 100 页两次 | 300 | 约 6000 | 只对两次观察中真正发生变化的 ID调用详情 |
| 两个接口都每 12 小时 100 页 | 400 | 约 8000 | 不是自动产生 8000 次详情；必须经过台账去重和变化判断 |

因此，400 次列表 API 请求理论上对应约 8000 条列表观察记录，但不等于 8000 个新帖子，也不等于 8000 次详情。若把每条列表记录都直接转成详情任务，详情额度会被迅速耗尽；详情任务数应由“新 ID 数量 + 已有 ID 中确实发生源端变化的数量”决定。

2026-08-12 06:07（北京时间）用旧 cookie 做了 29 次低强度跳页抽样，其中 `lists` 13 次、`lists2` 16 次，均成功且没有调用详情。结合 `create_time` 的边界，`lists` 当前约有 280–300 个新帖子/24 小时，中心估计约 290；结合 `lists2` 的 `update_time`，当前约有 380–420 个活跃/更新 ID/24 小时，中心估计约 400。后一个数字不是新增评论数：详情可能发现评论没有变化，例如评论出现后又被删除。

这次抽样还显示 `lists2` 的页码与 `update_time` 不是完全严格单调排序：较后页仍可能出现比前页更新的记录。因此 `lists2` 不能用“第一个详情没有变化”作为停止条件，必须记录列表事件本身，并使用整页稳定性、最小扫描深度和最大页数共同决定停止。

## 4. Cookie lane 分工

### 4.1 旧 cookie：实验/测量 lane

旧 cookie 只用于低强度实验、接口行为核对和收益测量，不作为生产队列的默认执行者。这里的“不定量”只表示本文不预先假设它每天有多少可用额度，并不表示它无限可用；它仍受真实 session 授权、上游速率和每日限额影响。

旧 lane 的实验请求应有独立的 run 标识和统计，不应悄悄混入生产成功数。若实验需要调用详情，应使用明确指定的测试 ID 或 shadow 队列，并在领取前检查生产队列，避免与新 lane 重复。

### 4.2 新 cookie：生产 crawler lane

新 cookie 作为正式列表扫描和详情补全的默认 lane。它只领取共享队列中已经通过去重和刷新判断的任务，并按自己的日预算、释放时间、单请求间隔和暂停状态运行。

两个 lane 必须分别计数 `lists`、`lists2`、`info` 和错误类型；不得把一个 lane 的剩余额度假定为另一个 lane 的剩余额度，也不得在一个 lane 返回 `rate_limited` 后自动切换另一个 lane 来规避限制。

真实 cookie 仍只由现有 client/config 读取；台账模块本身不保存 cookie，也不发请求。正式调度继续由一个 scheduler 进程、一个去重队列和统一 quota 计数负责，不把两个 lane 变成两个并发 worker。

## 5. ID 台账设计

### 5.1 记录分层

建议把“帖子当前内容”“帖子被列表观察到的状态”和“等待执行的详情任务”分成三个概念：帖子内容继续由现有 `posts` 保存，新增一个轻量的 ID 台账保存列表观察与详情时间线，`crawler_queue` 继续保存待执行任务。这样不会把“列表刚刚看到”误当成“详情刚刚成功抓取”。

建议的台账可以命名为 `post_id_ledger`，每个 `post_id` 只有一行：

| 字段 | 含义 |
|---|---|
| `post_id` | 规范化主键，唯一标识帖子 |
| `first_seen_at` | 本地第一次从列表接口观察到该 ID 的时间 |
| `last_list_seen_at` | 最近一次从任一列表接口观察到该 ID 的本地时间 |
| `last_lists_seen_at` | 最近一次从 `lists` 观察到该 ID 的本地时间 |
| `last_lists2_seen_at` | 最近一次从 `lists2` 观察到该 ID 的本地时间 |
| `source_create_time` | API 返回的帖子创建时间，不是本地抓取时间 |
| `source_update_time` | API 返回的帖子更新时间，不是本地抓取时间 |
| `source_comment_count` | 最近一次列表观察到的评论数 |
| `source_star_count` | 最近一次列表观察到的点赞数 |
| `source_trace_count` | 最近一次列表观察到的其他互动数 |
| `seen_via` | 最近一次或累计出现于 `lists`、`lists2` 的来源标记 |
| `source_presence_status` | `unknown`、`observed_in_list`、`confirmed_present`、`not_found_candidate`、`confirmed_unavailable`、`transient_error` |
| `presence_checked_at` | 最近一次用列表或详情检查源端存在性的本地时间 |
| `not_found_streak` | 连续独立详情检查得到 `not_found` 的次数；一次失败不能直接判定删除 |
| `last_lists2_event_key` | 最近一次 `lists2` 观察事件的去重键，通常由 `update_time`、`count_comment`、`refresh_time` 等字段组成 |
| `last_lists2_event_seen_at` | 最近一次看到该列表事件的本地时间 |
| `last_lists2_detail_attempt_at` | 最近一次因 `lists2` 事件发起详情尝试的时间 |
| `last_lists2_detail_result` | `changed`、`unchanged`、`not_found`、`transient_error`、`rate_limited` 等结果 |
| `needs_detail` | 是否有待执行的详情刷新需求 |
| `last_detail_started_at` | 最近一次开始调用详情接口的本地时间 |
| `last_detail_finished_at` | 最近一次详情调用结束的本地时间，无论成功失败 |
| `last_detail_success_at` | 最近一次成功保存详情的本地时间 |
| `last_detail_source_update_time` | 最近一次成功详情对应的源端更新时间 |
| `detail_comment_count` | 最近一次成功详情实际保存的评论数 |
| `detail_status` | `never`、`queued`、`running`、`succeeded`、`failed` 等状态 |
| `next_detail_at` | 下一次允许尝试详情的时间 |
| `last_detail_error` | 最近一次失败的归类错误，不保存 cookie |

时间字段应使用带时区的统一存储格式，界面展示时再转换为北京时间。`source_update_time` 是源 API 的业务时间，`last_lists2_seen_at` 是本地看到它的时间，`last_detail_success_at` 是详情真正成功的时间，三者不能互相替代。

### 5.2 与现有表的关系

现有 `posts` 已有部分源端更新时间和本地观察字段，`crawler_queue` 也已有列表评论数、最近尝试时间、状态和 claim 字段；这些字段可以复用或迁移，但当前并没有一个清晰的、专门表达 `last_detail_started_at` 与 `last_detail_success_at` 的完整时间线。因此下一阶段实现前要先核对迁移成本，不能直接把 `posts.updated_at` 当作详情成功时间。

一行台账只能保存某个 ID 的最新状态，不能完整保存同一帖子一天内多次出现的 `lists2` 事件。因此建议增加轻量的 `list2_observation_log`，至少记录 `post_id`、`event_key`、`observed_at`、扫描 run、页码、列表更新时间、列表评论数、是否进入详情、详情结果；唯一键可设为 `(post_id, event_key)`。这样“评论短暂出现后又删除”的事件即使详情最终 `unchanged`，也会被标记为已经消费，不能把它误当作本轮没有新列表事件。

## 6. 什么时候创建详情任务

### 6.1 `lists`：发现和首次补全

当 `lists` 发现一个台账中不存在的 ID 时，先插入台账并保存列表元数据；如果该帖子属于本项目的采集范围，则创建一次初始详情任务，以便获得正文、评论和回复结构。

当 `lists` 再次看到一个已经存在且详情已经成功的 ID 时，只更新列表观察字段；除非源端更新时间或评论数发生变化，否则不因为“又看到一次”而重复调用详情。

### 6.2 `lists2`：已有 ID 的更新触发器

当 `lists2` 看到一个已经存在于 ID 台账的 ID 时，比较新的 `source_update_time` 和 `source_comment_count`：只要源端更新时间前进，或列表评论数大于台账/最近详情记录的评论数，就把该 ID 标记为 `needs_detail` 并进入刷新队列。

当 `lists2` 看到一个台账中尚不存在的 ID 时，也插入台账并追加到详情队列尾部；它不会因为来自活跃流而抢占 priority 0 的已有 ID 更新任务。之后若 `lists` 再看到同一个 ID，两个来源只合并到同一队列行。

### 6.3 `lists2` 事件与详情无变化

每一条 `lists2` 记录先根据 `post_id` 和源端字段生成 `event_key`，再与 `list2_observation_log` 比较。只要 `event_key` 是新的，就记录一次列表事件；若该 ID 已在台账中，则按策略创建一次详情任务，即使上一次详情最后没有新增评论。

详情返回 `unchanged` 只表示“这一次详情快照没有比数据库多出可保存内容”，不表示列表事件不存在，也不表示后面的列表页可以跳过。详情结果只更新事件日志和台账，不改变本轮 `lists2` 的页级停止判断。

若详情返回 `not_found`，先把 `source_presence_status` 设为 `not_found_candidate`，增加 `not_found_streak`，保留 ID 和事件日志；只有在不同扫描轮次得到足够的独立 `not_found` 证据后才标记为 `confirmed_unavailable`。超时、限流、网络错误统一记为 `transient_error` 或对应错误，不得当作帖子被删除。

### 6.4 两个列表同时看到同一个 ID

两个列表来源都只通过 `post_id` 合并，不按标题、昵称或时间猜测是否相同。一个 ID 可以合并多个触发原因，但只能存在一个未完成的详情任务；`lists2` 的评论增长触发应优先于普通新帖任务。

## 7. 详情队列和不冲突规则

详情队列应保持 `post_id` 唯一约束。新帖发现、评论增长、更新时间前进等多个信号到达同一 ID 时，只更新任务的优先级、触发原因和最新源端快照，不创建第二个任务。

领取任务时使用现有的原子 claim 机制，至少记录 `lane_id`、claim token、开始时间和租约结束时间。只有持有有效 claim 的 lane 才能调用详情和写入该任务的成功结果；超时任务可以由调度器回收，但回收前要避免旧 worker 继续写入。

新 lane 的生产任务和旧 lane 的实验任务默认使用不同队列：生产任务写入正式 `posts`，实验任务写入实验 run 记录或只做只读比较。即使实验结果最终要入库，也必须先按 `post_id` 检查生产队列和最近成功时间，不能让两个 lane 同爬同一个 ID。

详情成功后同时更新台账和 `posts`：写入 `last_detail_success_at`、详情对应的 `source_update_time`、实际评论数和结果状态；列表观察只更新列表字段，不覆盖详情成功时间。

## 8. 建议的扫描节奏

当前 Railway 采用低强度监视模式：`lists` 每小时一次，`lists2` 每 30 分钟一次；每轮至少读取两页，通常在连续两页无队列变化、无新台账事件后停止，单轮最多 5 页。页级重复、空页、quota fuse 仍然是独立停止条件。

| 任务 | 经济模式 | 轻量监视模式 | 说明 |
|---|---|---|---|
| 初始 `lists` 建表 | 一次 20 页，只写 ID 台账和详情队列 | 一次 20 页，只写 ID 台账和详情队列 | 详情按发现顺序慢慢补；切换时暂停旧 coverage，先补一次 list1 再启动监视 |
| 增量 `lists` | 每小时至少 1 页，按需扩到最多 5 页 | 同左 | 完整处理一页；整页已知且无新事件后停止 |
| `lists2` 监视 | 每 30 分钟，至少 2 页、最多 5 页 | 同左 | 用事件日志和连续稳定页停止，不依据第一条详情结果停止 |
| 详情 `info` | 持续、单队列、低并发 | 持续、单队列、低并发 | 只消费去重后的新 ID 或新列表事件 |
| 实验扫描 | 旧 cookie 按需低强度 | 旧 cookie 按需低强度 | 不接管新 cookie 的生产队列 |

初始 20 页约产生 380–400 条列表观察记录；这一步只消耗 20 次列表请求，不写正文 stub。随后唯一 ID 按 `crawler_queue.queue_order` 进入详情队列，由 `trickle-fill` 串行补正文、评论和回复；成功或明确判定不可用后才视为完成。稳定运行时，`lists` 按当前约 290 个新帖/日的观测量，通常每小时一页即可，遇到突发时扩页；`lists2` 每 30 分钟低强度扫描，使用事件日志和连续稳定页停止。

半小时扫描仍不能保证捕捉所有“出现后很快被删除”的 `lists2` 事件；但每次返回的事件键会先落到 `list2_observation_log`，详情结果为 unchanged 也不会让本轮提前停止。

每轮扫描应串行或保持极低并发，使用已有的配额窗口、随机但有界的请求间隔和 `rate_limited` 次日暂停规则。随机间隔只用于保持正常的低强度调度，不是规避识别或突破限额的手段。

## 9. 扫描停止和重复判断

### 9.1 `lists` 的页级停止

初始建表固定处理 20 页，不提前使用“无收益页”停止；每条记录只建立 ID 台账和一个去重详情任务，并记录 `first_seen_source=lists`、扫描时间和发现顺序。增量扫描至少完成两页，并处理每页的全部返回记录；“看到一个已知 ID”不是停止条件，因为同一页后面仍可能有未知 ID。只有连续两页没有新的队列变化、没有新的台账事件时，才允许提前停止；首页实际返回 19 条时按返回记录判断，不强行要求 20 条。

首次上线或经历长时间中断后的前几轮仍要求连续两页稳定再停；每轮最多扩展到 5 页，防止突发发帖把单轮请求量无限放大；未覆盖的更深页面由下一小时继续处理。

### 9.2 `lists2` 的事件级和页级停止

`lists2` 每页的每个 ID 都先经过事件键去重。事件键已经在日志中出现时，不重复创建详情任务；事件键首次出现时，即使该 ID 上一次详情结果为 `unchanged`，仍记录并按策略尝试一次详情。这样删除评论造成的短暂列表事件不会因为详情没有新增内容而提前截断扫描。

首次 `lists2` 扫描是基线扫描：记录已有事件但不把整批历史事件转成详情任务。基线完成后，每轮至少两页、最多五页；只有连续两页事件键已见、没有新的已知 ID 触发详情时才允许停止。由于 `lists2` 的排序并非严格按 `update_time`，这只是有审计记录的保守启发式，不能宣称绝对无漏。

帖子存在性不参与“是否有新事件”的简单计数：已确认不可用的 ID 如果再次以同一事件键出现，视为已知稳定记录，不阻止停止；临时错误和单次 `not_found` 也不应被当作新 ID 或删除确认。

每轮应记录：页数、请求数、返回行数、唯一 ID 数、新 ID 数、新事件键数、重复事件键数、存在性状态变化、评论增长数、更新时间前进数、创建的详情任务数、详情 `unchanged` 数、被去重的任务数、无收益页数和最终停止原因。

## 10. 额度和收益核算

本轮估算的基准是：`lists` 约 290 个新帖/24 小时，`lists2` 约 400 个活跃/更新 ID/24 小时；这是列表观察量，不是详情成功量，也不是新增评论量。

| 方案 | `lists` 列表请求/日 | `lists2` 列表请求/日 | 列表请求合计/日 | 说明 |
|---|---:|---:|---:|---|
| 初始建表当天 | 20 列表请求 | 0 次（建表阶段） | 20 次 | 先建 ID 台账和详情队列；详情由后续低速任务消耗 |
| 当前低强度稳定运行（理论上限） | 约 24–120 | 约 48–240 | 约 72–360 | list1 每小时、list2 每 30 分钟；每轮 1–5 页，通常由稳定页提前停止 |

详情请求应单独估算：首次补全的新帖最多约 290 次/日；`lists2` 发现的新事件约 400 个/日，但其中可能有未知 ID、与新帖重复的 ID、同一 ID 的重复事件以及详情 `unchanged` 事件。因此在“每个新事件最多尝试一次详情”的规则下，详情理论上限约为 `290 + 400 = 690` 次/日，实际值应低于这个上限，必须由事件日志的去重率和 `lists`/`lists2` 交集测量。

详情请求仍由 `trickle-fill` 的独立预算和单线程间隔控制；列表请求上限只是最坏情况，不代表每天一定会用满。实际请求量要从 quota history 的 `new_list_calls`、`active_list_calls`、`detail_calls` 和 ledger 每轮收益统计中核算，不能把页数直接当成详情数。

初始建表当天固定约需 20 次列表请求；随后最多约 400 个唯一 ID 各需一次详情请求，但这些请求不与建表请求绑定，可按每日详情预算和 8–14 秒间隔慢慢完成。旧 coverage 详情未全部成功时，仍可启动 list1/list2 监测，但旧任务不会抢占详情队列；新回 priority 0 刷新和切换后新 ID 仍按原有额度与去重规则运行。

旧 cookie 和新 cookie 的请求必须分别记录；上述数字是单个生产 lane 的估算，不把旧 cookie 的实验请求算进生产覆盖量。列表和详情在上游仍可能共享同一 session 额度，内部把它们分成不同预算不代表真实上游额度彼此独立。

每个 lane 至少维护以下四类计数：列表请求数、详情请求数、成功详情数、限流/失效错误数。详情收益再拆成首次补全数、评论增长数、正文更新数、事件 `unchanged` 数和存在性确认数。

旧 lane 的实验报告和新 lane 的生产报告必须分开；生产报告至少要能回答“新 cookie 今天用了多少次列表/详情、成功补了多少 ID、消费了多少新 `lists2` 事件、是否触发限流、队列是否积压”，实验报告则回答“某个 API 字段或刷新规则是否成立”。

## 11. 当前实现和验收状态

1. `storage/post_writer.py` 在 runtime schema 阶段创建/迁移 `post_id_ledger`、`list2_observation_log` 和 `ledger_state`。
2. `crawler/service.py` 在每次 list page 后记录首次来源、页码、rank、发现顺序、源端时间和事件键；bootstrap list1 只建立台账和详情队列，list2 首次扫描建立基线，后续新事件才进入同一个 `crawler_queue`。
3. `trickle-fill` 在详情开始、成功、部分响应、not_found、失败或 quota 阻断时回写详情时间线；队列的 `post_id` 主键继续保证两个 lane 不会同时领取同一帖子。
4. `jobs/scheduler.py` 首次只运行一次 20 页 list1 bootstrap；bootstrap 完成后持久化 queue-order cutover，暂停切换前的普通 coverage 任务，先安排一次 list1，再开启 list1=3600 秒、list2=1800 秒的监测。每轮默认最少两页、最多五页，并继续使用逐请求 quota、随机低速间隔和 rate-limit 次日暂停。
5. `crawler_queue.queue_order` 保证初始和后续 coverage 任务按首次发现顺序追加；list2 更新任务进入 priority 0 车道并受 refresh limit 约束。
6. `tests/test_id_ledger.py` 和 `tests/test_bootstrap_queue.py` 覆盖首次来源/发现顺序、稳定重放、20 页 bootstrap、list2 基线和新事件；既有 crawler、scheduler、quota 回归测试继续运行。

Railway 上的 bootstrap 会把 20 页结果写入线上 Volume 的 ID 台账和详情队列，但不会把本地 397 条快照自动覆盖线上 Volume；只有详情成功或明确不可用的行才会离开初始待处理集合，不会把“列表已见”误报成“详情已成功”。

## 12. 上线后的核对

部署后先看一轮低强度调度的 `crawler_run_history` 和 quota history：确认 list1/list2 的实际页数会在稳定页处停止，详情只来自新增 ID 或新事件，且相同 `post_id` 没有重复 pending 任务。Railway 查询仍通过 Volume 内的 `/opt/venv/bin/python -`，不使用 `sqlite3` CLI，也不把 cookie 值写入日志。
